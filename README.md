# Учебный DWH для e-commerce: Olist + ClickHouse

Учебный аналитический контур на открытых данных бразильского маркетплейса Olist. Это не production-опыт, а проект, чтобы собрать руками слои хранилища, единые определения метрик и проверки качества данных.

**Стек:** ClickHouse (Docker), dbt, HTML-дашборд по витрине.

## Слои

Слои разделены базами данных в ClickHouse.

| Слой | База | Что внутри |
| --- | --- | --- |
| raw | `raw` | Данные Olist как в CSV, типы заданы вручную |
| stg | `stg` | Очистка, переименование, приведение типов |
| cdm | `cdm` | Единые сущности: покупатели, заказы, товары |
| marts | `marts` | Бизнес-витрины под метрики и дашборд |

## Запуск

```
cd C:\olist-dwh
docker compose up -d
docker exec -it ch clickhouse-client --user admin --password dev
```

Пароль `dev` только для локального учебного стенда. CSV лежат в `data/` и подключены в контейнер как `olist/` (чтение через `file('olist/...', CSVWithNames)`).

## Загрузка raw

Загрузка идемпотентна: перед повторным запуском `TRUNCATE TABLE`, затем `INSERT`. MergeTree не отсеивает дубли, и повторный `INSERT` без очистки удваивает строки (так и было при первой загрузке `raw.orders`: 198 882 строки при 99 441 уникальном заказе).

| Таблица | Строк | Ключ сортировки |
| --- | --- | --- |
| `raw.orders` | 99 441 | `order_id` |
| `raw.order_items` | 112 650 | `(order_id, order_item_id)` |
| `raw.customers` | 99 441 | `customer_id` |
| `raw.order_payments` | 103 886 | `(order_id, payment_sequential)` |
| `raw.sellers` | 3 095 | `seller_id` |
| `raw.products` | 32 951 | `product_id` |
| `raw.product_category_name_translation` | 71 | `product_category_name` |

Всю загрузку воспроизводит один файл: `sql/01_raw.sql` (в конце он сам печатает контрольные числа). Таблицы `geolocation` (около миллиона строк, для метрик не нужна) и `order_reviews` (текст с переносами строк) сознательно не загружаем.

## dbt

Проект `olist_dwh/` (dbt-core 1.12 + dbt-clickhouse 1.10, окружение в `.venv/`). Профиль подключения лежит вне репозитория (`~/.dbt/profiles.yml`).

```
cd olist_dwh
..\.venv\Scripts\dbt.exe run                          # собрать все модели
..\.venv\Scripts\dbt.exe run --select stg_products    # только одну
```

- **Слои = базы ClickHouse:** макрос `generate_schema_name` кладёт модели слоя ровно в базу `stg`, `cdm` или `marts` (без префикса `stg_stg`).
- **Источники** описаны в `models/stg/_sources.yml`; модели обращаются к ним через `source('raw', ...)`, так dbt знает зависимости, а адрес таблицы задан в одном месте.
- **stg:** по одной модели на таблицу raw (`stg_orders`, `stg_order_items`, `stg_order_payments`, `stg_customers`, `stg_sellers`, `stg_products`, `stg_product_category_name_translation`), материализация `view`. Только очистка: исправлены опечатки источника `product_name_lenght` → `product_name_length` и `product_description_lenght` → `product_description_length`. Бизнес-логики и фильтров в stg нет. Число строк в каждом представлении совпадает с raw.

## Слой cdm

Три таблицы (материализация `table`, база `cdm`):

| Модель | Grain | Проверка |
| --- | --- | --- |
| `fct_orders` | 1 строка = 1 заказ | 99 441 строка; сумма `items_price` = сумме `price` в raw (13 591 643,70) |
| `dim_customers` | 1 строка = 1 человек (`customer_unique_id`) | 96 096 людей; сумма `orders_count` = 99 441; повторных покупателей 2 997 (около 3%) |
| `dim_products` | 1 строка = 1 товар (`product_id`) | 32 951 товар; 623 с категорией `unknown` |

Решения:
- **Позиции и платежи приводятся к grain заказа до соединения** (отдельные CTE с `GROUP BY order_id`), иначе заказ с 3 товарами и 2 платежами даёт 6 строк, а выручка по позициям удваивается.
- **`left join` с `join_use_nulls = 1`:** заказ без товаров или платежа получает `NULL`, а не 0 (отсутствие данных не равно нулевой сумме).
- **Город и штат покупателя** берутся из последнего заказа: `argMax(city, order_purchase_timestamp)`.
- **Категории:** 610 товаров без категории и 13 товаров из двух категорий без перевода получают `unknown` в английской колонке; исходная колонка `product_category_name` сохранена, чтобы различать причины.
- **Особенность ClickHouse:** если колонка с одним именем есть в нескольких таблицах `JOIN`, в результате она получает имя с префиксом (`o.order_id`). Поэтому ключи в моделях называются явно через `as`. Ошибку поймал тест `unique`.

## Витрина и дерево метрик

`marts.mart_revenue_monthly` — grain: 1 строка = 1 месяц покупки, только доставленные заказы (`order_status = 'delivered'`).

**Определение:** выручка = сумма `price` по доставленным заказам (без `freight_value`), месяц по дате покупки.

**Дерево метрик** (везде один и тот же фильтр `delivered`):

```
Выручка          = заказы × средний чек
заказы           = покупатели × заказов на покупателя
средний чек      = товаров в заказе × средняя цена товара
```

| Метрика | Формула |
| --- | --- |
| `buyers` | `uniqExact(customer_unique_id)` среди доставленных заказов месяца |
| `orders` | число доставленных заказов |
| `items` | сумма `items_count` |
| `revenue` | сумма `items_price` |
| `orders_per_buyer` | `orders / buyers` |
| `items_per_order` | `items / orders` |
| `avg_item_price` | `revenue / items` |
| `aov` (средний чек) | `revenue / orders` = `items_per_order × avg_item_price` |

**Сверка:** 96 478 заказов в сумме по месяцам (всего доставленных), выручка 13 221 498,11 совпала с прямым подсчётом по `raw.order_items` + `raw.orders`. Дерево сходится точно: чек равен товарам в заказе × цену товара.

**Ограничения:** `dim_customers.orders_count` считает все заказы человека, поэтому для дерева метрик не используется (витрина считает доставленные заново из `fct_orders`). Выручка не включает доставку.

## Тесты качества данных

`dbt test` (10 проверок на слое stg, все проходят):

| Что проверяется | Тест |
| --- | --- |
| `order_id` уникален и не пуст | `unique`, `not_null` |
| `order_status` из допустимого списка (8 значений) | `accepted_values` |
| У каждого заказа есть покупатель | `not_null` + `relationships` на `stg_customers` |
| `customer_id` в `stg_customers` уникален и не пуст | `unique`, `not_null` |
| Каждая позиция относится к существующему заказу | `not_null` + `relationships` на `stg_orders` |
| Цена, доставка и платежи не отрицательны | единичный тест `tests/assert_amounts_non_negative.sql` |

Тест на уникальность проверен «в бою»: дубль строки в `raw.orders` дал `FAIL 1`, после `TRUNCATE` + повторной загрузки все тесты снова проходят. Тот же дубль мы раньше нашли руками (двойная загрузка).

Задокументированные исключения, которые тесты не проверяют: один доставленный заказ без платежа, 775 заказов без товаров (нет среди них `delivered`).

## Решения по ClickHouse

- **Ключ сортировки подбирается под чтение.** Проверено опытом: копия `raw.orders` с ключом `(toStartOfMonth(order_purchase_timestamp), order_id)` читает за один месяц 16,38 тыс. строк против 99,44 тыс. у таблицы с ключом `order_id` (разреженный индекс пропускает блоки по 8 192 строки). Для `raw` оставляем нейтральный `order_id` (читают по-разному), месяц ставим первым в ключ витрин (их читают по месяцам).
- **`PARTITION BY` не используем в raw.** Партиции нужны для управления данными (удалить старый месяц), а не для скорости; на 99 тыс. строк они лишние. В витрине можно по месяцу (`toYYYYMM`), но не мельче.
- **Почему ClickHouse, а не PostgreSQL:** колоночное хранение. Запрос про сумму цен по месяцам читает только нужные колонки (в опыте выше 397,76 КБ = 99 440 строк × 4 байта одной колонки `DateTime`), колонки лучше сжимаются. PostgreSQL остаётся лучше для операционных данных: точечные чтения и правки, транзакции.
- **Где сломается при росте ×10:** `JOIN` больших таблиц упирается в память (правая таблица грузится в оперативку), один сервер упирается в диск, загрузка `TRUNCATE` + `INSERT` не годится, нужна инкрементальная.

## Особенности данных

- **Двойная загрузка:** `MergeTree` не отсеивает дубли, повторный `INSERT` без `TRUNCATE` удвоил строки `raw.orders`. Поймано сравнением `count()` и `uniqExact(order_id)`.
- **`customer_id` и `customer_unique_id`:** `customer_id` выдаётся на каждый заказ (99 441 значение), `customer_unique_id` обозначает человека (96 096). Метрики по покупателям считаем по `customer_unique_id`.
- **Заказ без платежа:** один доставленный заказ (`bfbd0f9bdef84302105ad712db648a6c`) не имеет платежей. Исключение документируем, не удаляем.
- **Заказы без товаров:** в `order_items` только 98 666 заказов из 99 441. У 775 заказов нет позиций: `unavailable` 603, `canceled` 164, `created` 5, `invoiced` 2, `shipped` 1. Среди них нет `delivered`, поэтому на выручку по доставленным заказам это не влияет. Любая метрика через `order_items` эти заказы не видит. Один заказ в статусе `shipped` без товаров считаем аномалией источника.
- **Несколько платежей на заказ:** в `order_payments` 103 886 строк на 99 440 заказов. Перед `JOIN` приводим к grain заказа, иначе строки размножаются.
- **`LEFT JOIN` в ClickHouse:** для несовпавших строк вместо `NULL` подставляется значение по умолчанию (`''`). Для поиска «нет ни одного» используем `LEFT ANTI JOIN` или `join_use_nulls = 1`.
- **Товары без карточки:** у 610 товаров нет категории, названия, описания и фото, у 2 нет габаритов.
- **Категории без перевода:** `pc_gamer` и `portateis_cozinha_e_preparadores_de_alimentos` отсутствуют в таблице перевода, закрываем в stg.
- **Опечатки источника:** колонки `product_name_lenght` и `product_description_lenght`. Raw повторяет источник, исправляем в stg.

Контрольная сверка после загрузки: `count()` в таблице совпадает с `count()` по файлу, а `count()` и `uniqExact(order_id)` в `raw.orders` равны.

`ORDER BY` в ClickHouse задаёт порядок хранения и первичный индекс, а не уникальность. `order_id` выбран ключом, потому что таблицы чаще всего соединяются по нему.

## Типы данных

- Деньги (`price`, `freight_value`): `Decimal(10, 2)`, а не `Float64`, чтобы суммы были точными (у float `0.1 + 0.2` не равно `0.3`).
- `Nullable` только там, где пустые значения подтверждены данными (`countIf(col IS NULL)`). В `raw.orders` это даты одобрения, передачи перевозчику и доставки клиенту. В `raw.order_items` пустых значений нет.

## Определения метрик

### Выручка по доставленным заказам

- **Формула:** сумма `price` из `order_items` по заказам со статусом `delivered`. Стоимость доставки (`freight_value`) не входит.
- **Дата отнесения к периоду:** `order_purchase_timestamp` (месяц покупки).
- **Почему только `delivered`:** остальные статусы либо отмены (`canceled`, `unavailable`), либо промежуточные (`created`, `approved`, `invoiced`, `processing`, `shipped`), то есть сделка не завершена.
- **Ограничение:** последние месяцы выгрузки занижены, потому что часть заказов ещё в пути (`shipped`, `invoiced`, `processing`). Спад в конце графика может быть артефактом.
- **Сверка с «всеми заказами»:** в зрелых месяцах расхождение по сумме до 3%. В первых месяцах оно достигает 98%, но база там очень маленькая (единицы заказов), процент не показателен.

Строка в `order_items` соответствует товару, а не заказу. Для суммы `price` это безопасно, а заказы считаются через `uniqExact(order_id)`.

Допустимые значения `order_status` (для dbt-теста `accepted_values`): `delivered`, `shipped`, `canceled`, `unavailable`, `invoiced`, `processing`, `created`, `approved`.
